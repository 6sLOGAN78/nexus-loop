# Nexus Loop — simple guide

## The problem, in normal language

A company already has an AI support agent running on WhatsApp. It uses an LLM, prompts, a knowledge base, APIs/tools, and human handoff. Every conversation produces logs.

When the bot becomes worse, people currently discover it from complaints. Someone then reads chats, guesses what changed, edits a prompt or configuration, and hopes the edit helped.

We have to build a small “agent improvement system” that does this job more systematically:

1. reads the logs;
2. notices a real problem;
3. explains the likely reason;
4. suggests one small fix;
5. tests the fix using a replay service;
6. gives a human an approve/reject button.

This is not a task to build another chatbot. It is a task to build a **quality-control loop for an existing agent**.

## What we submit

There are only two main outputs.

1. `loop-report.json`: a JSON file generated by our code. It contains our metrics, findings, diagnoses, things we cannot measure, and optionally proposed fixes and replay results.
2. One screen: a person should be able to see an issue, understand the evidence, and approve or reject a proposed fix.

The “product” part means the screen must help an operator make a decision. It should not just be charts.

A good screen answers:

- what broke?
- who was affected?
- how bad is it?
- why do we think it happened?
- who needs to fix it?
- what are we asking permission to change?
- what could go wrong if our diagnosis is wrong?
- did the replay test say the fix helped?

## A running example

Imagine this pattern in the logs:

- users asking “where is my order?” used to resolve their problem 85% of the time;
- after a tool update, that falls to 77%;
- the API still says HTTP 200 and `outcome = ok`;
- but some responses are empty, so the agent has nothing useful to say;
- it retries, apologises, then hands users off or leaves them unresolved.

Our system should produce a conclusion like this:

> “The order-status cohort became worse after the order-status tool updated. The tool is technically successful but returns empty data for some users. We recommend treating an empty response as a tool failure and using a fallback. This should be approved only after the orders team confirms that an empty response is never a valid business state.”

That is the level of practical reasoning the problem wants.

The practice dataset contains:

Use `corpus_sample/` first because it is a 5% slice containing whole conversations. Once a finding looks real, confirm it on `corpus/`, the full dataset.

## The important files

| File | What it means | Why we need it |
|---|---|---|
| `catalog.json` | The rulebook for the data | Read this first. It says which joins are safe, what a field means, and what cannot be measured. |
| `asks.md` | Eleven questions written like an operator would ask them | Our system must answer or honestly refuse these questions. |

| `examples/` | Level 1, 2, and 3 reports | Useful examples of what a good report looks like. |

## Do not confuse the three data levels

This is the most likely data mistake.

- A **session** is one whole customer conversation.
- A **step** is one internal action inside that conversation, such as an LLM call or tool call.
- A **turn** is one user/agent exchange containing text.

One session has many steps. If we blindly join steps onto sessions and then count sessions, we can accidentally count the same conversation many times.

Simple rule: if the final metric is “per conversation,” first reduce the step data back to one value per conversation.

Also: transcripts are not proof of a technical cause. A timeout, a tool 500, a KB miss, and a guardrail block can all make the agent write a similar apology. Use agent-step data to identify the actual cause.

# What the practice data contains

The practice kit includes an answer key so teams can learn. It must not be hardcoded because the sealed dataset moves the same kinds of issues to different days, tenants, and cohorts.

## The three real problems

### 1. New premium-card questions have no knowledge-base coverage

- Tenant: Acme Bank
- Cohort: `premium_card_info`
- Starts: day 34
- Cause: `kb.gap`
- What happens: this is a new product line. Retrieval gets no confident document, so the agent gives a generic answer instead of answering the question.
- Effect: its resolution rate is about 31%, while comparable healthy traffic is above 80%.
- Why this is tricky: this cohort did not exist before day 34, so there is no “before” period. We must compare it with similar successful question-answering intents or the agent’s own best conversations.
- Sensible fix: add approved premium-card material to the KB or add retrieval synonyms.
- Agentic lesson: a new intent can be born broken. Prompt quality does not solve missing knowledge.

### 2. The order-status tool returns empty data while claiming success

- Tenant: Northwind Retail
- Cohort: `order_status` using `get_order_status`
- Starts: day 40
- Cause: `tool.contract_break`
- What happens: about 14% of calls return HTTP 200 and `outcome = ok`, but the payload is empty.
- Effect: order-status resolution falls from about 85% to 78%. The ordinary tool-error metric barely moves, so a basic error dashboard misses it.
- Evidence to inspect: `response_bytes`, `result_field_count`, and a retry of the same tool in the session.
- Sensible fix: validate that the result has expected fields. If it is empty, treat it as a failure and take an explicit fallback/handoff path.
- Agentic lesson: “the tool call succeeded” and “the agent received usable information” are different things.

### 3. A prompt creates unnecessary confirmation turns

- Tenant: Acme Bank
- Cohort: `acme_main_v3`
- Starts: day 46
- Cause: `prompt.regression`
- What happens: prompt v4 makes the agent over-confirm with users.
- Effect: median turns rise from 4 to 6; cost per session rises from roughly $0.044 to $0.080; resolution stays effectively flat.
- Why this is tricky: an outcome-only dashboard says nothing is wrong because users still eventually resolve.
- Sensible fix: edit or revert the prompt while checking that the same quality/resolution yardstick does not become worse.
- Agentic lesson: good agents are not just accurate; they must also be efficient and not waste user turns or money.

## The three false alarms we must dismiss

These are deliberately there to punish shallow analysis.

### Marketing/traffic mix shift

At Acme Bank, a campaign creates a huge rise in `branch_locator` traffic around day 22. Because branch locator is easy for the bot, aggregate containment rises. That does **not** prove the agent improved.

Correct response: compare within each intent. If individual intent behavior is stable, say this is a mix shift, not a quality change.

### Flash-sale load event

Northwind has a four-day flash sale around day 12. Traffic jumps to about 4× normal, tool p95 latency doubles, and timeouts rise. But customer quality is flat and the issue self-corrects.

Correct response: mention it as a temporary platform/reliability event if useful, but do not call it an agent-quality regression.

### Judge-version change

On day 28, a quality rubric changes from v1 to v2 for both tenants. Scores drop by about 0.6 at once.

Correct response: do not compare quality scores across the boundary. The measurement system changed, not necessarily the agent. Compare only within one `judge_version`, or re-score old data using the same judge.

# The honesty requirements

The organisers care a lot about not pretending we know more than we do.

## Coverage

Coverage means: “what fraction of traffic has the data needed for this metric?”

Legacy `v2_flow` sessions emit no tool-call, KB-lookup, or guardrail steps.

So a tool metric must say:

- Acme Bank tool coverage is about 72%;
- Northwind Retail tool coverage is about 93%.

We must exclude legacy sessions from a tool-call denominator. We must not treat “no tool log” as “a tool call with no error.”

## Fidelity

Every metric says how it was produced:

- **measured**: directly recorded in logs, e.g. handoff, API status, latency;
- **derived**: calculated from recorded fields, e.g. an HTTP-200 response with zero result fields;
- **judged**: an LLM or human decided something semantic, e.g. “did the user leave out of frustration?”

## Calibration

If we use an LLM judge, we compare it with supplied human labels and publish the agreement rate. Do not claim perfect agreement: humans themselves disagree in about 7.5% of the labels.

## Refusing a question is correct sometimes

Ask A11 asks for failover rate: “how often did a primary model/tool fail and an alternate serve the user?”

The runtime has no failover feature and logs no failover event. The correct answer is not “0%”; it is:

> “not measurable. We would need a step-level `failover` event containing `from_target`, `to_target`, `reason`, and `recovered`, owned by the conversation runtime.”

A retry is not a failover. It can be the same model retried at a different temperature.

# The four asks we should understand first

| Ask | Simple answer direction |
|---|---|
| A01: “what share did we handle end to end?” | Measured containment rate. Count resolved sessions plus handoffs that were by design. |
| A04: “how often did a tool call fail?” | Measured from tool-call logs. Do not use an LLM. State v3-only coverage. |
| A09: “how many users gave up out of frustration?” | Abandonment itself is measured. The reason “frustration” is semantic and needs an LLM judge plus calibration. |
| A11: “what is our failover rate?” | Not measurable. Explain the missing event rather than making up a proxy. |

# What “good work” looks like

For one problem, do the full loop well instead of shallowly detecting ten things.

1. **Find it:** “Northwind order-status resolution fell after day 40.”
2. **Define the group:** “order-status conversations using `get_order_status`, days 40–52.”
3. **Show impact:** count affected conversations, their share of traffic, extra handoffs/abandonments, extra cost if it can be computed.
4. **Explain why:** show empty-success tool responses and link them to the day-40 tool deployment.
5. **Propose one change:** “require non-empty order fields before giving the result to the LLM.”
6. **State the risk:** “an empty payload might be a legitimate order state.”
7. **State a no-ship condition:** “do not ship if the orders team says empty is valid, or if the golden set gets worse.”
8. **Replay it:** submit the change and exact cohort to the replay service.
9. **Let a human decide:** record accepted, rejected, or deferred, including a reason.

A rejected change with a good reason is still a successful product decision.

# What we need to build, practically

Keep it simple.

```text
read data
  ↓
calculate metrics and group by tenant / intent / day / config
  ↓
find suspicious cohorts
  ↓
check a fair baseline and config timeline
  ↓
write findings and diagnoses into JSON
  ↓
choose one fix and test it with replay
  ↓
show it on one screen with approve/reject
```

Suggested code pieces:

- data loader for gzipped JSONL;
- metrics functions;
- cohort/grouping functions;
- detector rules;
- config-change matching;
- report generator;
- replay client;
- minimal API/UI for the report and decision button.

Do not build a fancy multi-agent system unless it helps this loop. A deterministic Python pipeline plus a small, carefully used LLM judge is more aligned with the rules.

# A simple plan for the first days

## Day 1

- Run the starter and scoring scripts.
- Read `catalog.json` and `asks.md`.
- Generate one valid report.
- Add the A11 refusal.
- Learn the session/step/turn data model.

## Day 2

- Build reusable metrics for containment, resolution, handoff, turns, tool failure, empty-success tool responses, and KB hit rate.
- Attach fidelity and coverage to each metric.
- Start with the 5% sample.

## Day 3

- Group metrics by tenant, intent, day/week, agent, tool, and config version.
- Investigate candidates using fair comparisons.
- Write explicit non-regression findings for the marketing shift and judge change.

## Day 4

- Pick the clearest real issue.
- Mine a healthy standard from comparable successful conversations.
- Propose one small change and use replay.

## Day 5

- Connect generated report content to the screen.
- Make approve/reject save a real decision.
- Run the full corpus and the scorer from a clean command.

# A short interview explanation

> I see this as an agent-evaluation and improvement loop, not a chatbot project. We would use runtime logs to find a specific cohort that became worse, trace the issue through prompt, KB, tool, routing, or handoff behavior, and propose a narrow change. The important part is verifying that change against the same cohort and a golden set, while being honest about coverage and things the logs cannot tell us. That gives an operator evidence to approve or reject a safe agent update.
