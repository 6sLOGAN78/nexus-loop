# Nexus Loop — deliverables, replay, sealed run, and demo 

Source of truth: the official 12-page problem statement
`docs/YellowAI_PS_TechQuest (1).pdf`, cross-checked against the shipped kit
(`kit/` + `tools/nexus-loop-kit/`), `schema/loop-report.schema.json`, `score.py`,
and `replay/serve.py`. Where the PS and the kit differ, that is called out.

---

## 1. TL;DR

- **Two required deliverables:** (1) `loop-report.json` generated by your code
  and valid against the schema; (2) one operator screen with a working
  **APPROVE / REJECT** control that writes the human decision back into the
  report.
- **Plus a third submission item:** a one-page note stating what is real, what is
  stubbed, and what breaks at 100× scale.
- **What you build:** a small, unattended, deterministic Python system that
  reads logs → finds real problems → explains cause → proposes a fix → verifies
  it on the replay service → shows it on one screen → records the human decision.
  Not a chatbot, not a hosted platform.
- **The replay service is provided** (`replay/serve.py`). You call it. Each team
  gets **40 attempts**, counted per team name and audited at `GET /log`.
- **Sealed run:** at 12:00 on day 6 the system runs untouched on a hidden second
  corpus with the same kinds of problems moved. Unattended or it scores as failed.
- **Score:** 55 machine (script) + 45 human (decision quality 18, screen 15,
  framing 12) = 100.

---

## 2. The exact deliverables

### Deliverable 1 — `loop-report.json`

- Generated by your code, valid against `tools/nexus-loop-kit/schema/loop-report.schema.json`.
- **Produced from the sealed run without edits.** Hand-editing the report after
  the run is a violation; the system must emit the final file.
- The screen's approve/reject action must be **written back into this report**
  (the `prescriptions[].approval` block), so the submitted report contains the
  recorded human decision.
- Eight sections; **four required**: `metrics`, `findings`, `diagnoses`, `gaps`.
  **Four optional** (where the remaining machine points live): `standard`,
  `prescriptions`, `verifications`, `self_assessment`. Also `team`, `corpus`,
  `system_notes`, `generated_at`.

### Deliverable 2 — the screen

- "One screen a person can read and act from."
- Must contain a **working APPROVE / REJECT control** (schema also allows
  `deferred`).
- Must render the report's finding: the evidence behind it and the proposed fix.
- The decision must persist into the report with a reason.
- Test: "Would an operator who was not on your team know what to do on Monday
  morning after reading it?"

### Deliverable 3 — one-page note (submission requirement)

Must state:
- what is **real**,
- what is **stubbed**,
- what is **simulated**,
- what **breaks at 100× scale**.

"Faking is fine in six days. Hiding it is not."

## 3. Is this a "platform"? No.

The PS never asks for a platform, SaaS product, dashboard suite, or multi-tenant
service. It asks for:

1. **a system** — a runnable pipeline that produces the report, and
2. **one screen** — a single decision-support page.

What "system" means operationally (from the sealed-run rule): "A system that
needs hand-holding to run scores as if it failed." So the bar is a **one-command,
unattended run** on unseen data. The screen may be a tiny local HTTP app (you
need a server to persist a decision; a static HTML file cannot mutate the
report). No framework, database, auth, or cloud deployment is required.

What you do **not** build: the replay service (organisers provide it), the
scoring script, the data generator, or an LLM agent swarm. A deterministic Python
pipeline plus one small server is the intended shape.

## 4. What to report (the eight sections)

Required:

| Section | What goes in it | Schema must-haves |
|---|---|---|
| `metrics` | Every number you measured, with its plan | `id`, `ask_id`, `fidelity` (measured/derived/judged), `coverage{value,basis}`, `plan{source,filter,denominator}`; `calibration{agreement,n}` for judged, and never 1.00 |
| `findings` | What moved, **including what you decided was not a problem** | `id`, `tenant`, `cohort`, `metric`, `window{from_day,to_day}`, `is_regression`. If true: `impact{conversations_affected,share_of_traffic,derivation}`, `audience[]`, `if_nothing_changes`. If false: `not_a_regression_because` |
| `diagnoses` | Why it happened, including the blamed config change | `id`, `finding_id`, `cause_class` (enum), `attributed_change{kind,day}` |
| `gaps` | What you could not measure, with the exact event that would answer it | `ask_id`, `verdict`, `why`, `required_event{name,grain,fields,owner}` |

Optional:

| Section | What goes in it |
|---|---|
| `standard` | What "good" looks like, mined from the deployment's own best conversations (`cohort`, `metric`, `best`, `median`, `derivation`, golden-set version) |
| `prescriptions` | The proposed fix as a decision: `change_type`, `target`, `predicted_delta{metric,from,to}`, `decision{asking_approval_for, risk_if_diagnosis_wrong, would_not_ship_if}`, `approval{verdict,decided_by,reason,at}` |
| `verifications` | Replay evidence: `prescription_id`, `replay_run_id` (starts `rp_`), `before`, `after`, `golden_set_pass`, `verdict`, `prediction_error` |
| `self_assessment` | The system's own hit rate: `cycles`, `prescription_accuracy` keyed by change type, `downweighted` |

A finding is a **decision, not a number**. Every real finding must carry impact
(count, share of traffic, downstream users, duration, cost), an owner
(`agent_builder` / `business_owner` / `platform_owner`), a one-sentence
consequence of inaction, and a derivation naming the baseline and why it is fair.

## 5. Required operator questions

`asks.md` has 11 questions; the PS declares **four required: A01, A04, A09, A11.**
The system must either answer each or explain exactly why it cannot.

| Ask | Correct treatment |
|---|---|
| **A01** containment: share handled end to end | Measured `containment_rate` = resolved + by-design handoffs / all sessions |
| **A04** how often a tool call failed | **Measured** from tool-call logs; state v3-only coverage; using an LLM here is a Rule 1 violation |
| **A09** how many gave up from frustration | Abandonment is **measured**; the *reason* is **judged**. Build/version a judge with published calibration, or emit a `REQUIRES_NEW_JUDGE` gap. Do not infer reason from the session end code |
| **A11** failover rate | **NOT_MEASURABLE.** No failover mechanism exists. Refuse and specify the required event: `failover`, grain `step`, fields `from_target,to_target,reason,recovered`, owner `conversation-runtime`. Note that retry is not failover |

Answering the other seven (A02, A03, A05–A08, A10) with a metric or a gap is
cheap and helps the human framing score.

## 6. The four tasks (how deliverables map to work)

| Task | Work | Deliverable |
|---|---|---|
| **01 Detection & Diagnosis** | Find real problems, name the slice, quantify impact, identify cause, point at the config change, examine lookalikes, dismiss false alarms, identify what cannot be measured | The report's `metrics`, `findings`, `diagnoses`, `gaps` |
| **02 Standard & Fix Proposal** | Mine what "good" looks like from best conversations; identify deviations; propose one fix; state diagnosis risk; define no-ship condition | `standard` + `prescriptions`, surfaced on the screen for approval |
| **03 Fix Verification** | Use the replay service on the affected cohort; show before/after | `verifications` (real `rp_` run id) |
| **04 Decision Layer & Self-Assessment** | Record the human decision for each proposed fix; at the highest level keep the system's own hit rate | `prescriptions[].approval` + `self_assessment` |

## 7. What to show in the final report / final demo

### The report (sealed output)
The scored artefact is the sealed-run `loop-report.json` plus the screen and note.
It should show, in order: honest metrics with fidelity/coverage → the real
findings with impact and derivation → the dismissed lookalikes → the diagnoses
with blamed config changes → the proposed fix as a decision → replay before/after
→ the recorded human verdict → the A11 refusal with its event spec → the mined
standard → the self-assessment.

### The demo (10 minutes + 5 minutes Q&A)
Open on the **problem from the operator's side, not your architecture.** The PS
lists nine things to show:

1. The finding and its impact.
2. The lookalike you correctly ignored.
3. The diagnosis.
4. The configuration change behind it.
5. The proposed fix.
6. Proof the fix works (replay before/after).
7. The approval gate (working approve/reject, decision written back).
8. The one question your system refused to answer.
9. Why it refused.

"The refusal is the most memorable thirty seconds you have."

## 8. The replay service — the full scene

### What it is
`tools/nexus-loop-kit/replay/serve.py`, a local HTTP service. In
the practice week you run it yourself against the practice ground truth. On the
sealed run the organisers run it centrally against the hidden ground truth and
give teams a URL. It is a **hypothesis verifier**, not a discovery engine.

### Contract
`POST /replay` with JSON:

```json
{
  "team": "your-team",
  "tenant": "northwind-retail",
  "change": {"type": "tool.validate", "target": "get_order_status", "description": "..."},
  "cohort": {"intent": "order_status", "tool": "get_order_status", "from_day": 40, "to_day": 52},
  "golden_set": ["s_nort_000123", "..."]
}
```

Returns:

```json
{
  "run_id": "rp_...", "runs_used": 3, "run_budget": 40,
  "metric": "resolution_rate", "before": 0.7663, "after": 0.8524,
  "delta": 0.0861, "verdict": "improved",
  "golden_set": {"replayed": 30, "regressed": 0, "pass": true},
  "sessions_replayed": 412,
  "note": "a wrong fix returns no_effect. That is a result, not a failure."
}
```

Also available: `GET /health`, `GET /log` (audit of every call).

### How your tries are controlled
- `RUN_BUDGET = 40` **per team string** (`serve.py:38`). After 40, you get
  `run_budget_exhausted`.
- The counter is in-memory keyed by `team`; it starts at zero when the server
  starts and is audited at `GET /log`.
- A request missing `tenant` or `change.type` returns HTTP 400 and does **not**
  consume an attempt. Any request that passes that check **does** consume one,
  even if the cohort is wrong or the change type does not apply.
- **The endpoint is deterministic per `[tenant, change, cohort]`** (seeded hash).
  Re-sending the same call burns budget and returns the same answer. Do not
  probe repeatedly to "see variance".

### How a fix is decided
- A fix only moves anything if `change.type` is in the fault's
  `accepted_fix_classes`:
  - KB gap: `kb.add` (direct, strongest) or `kb.synonym`
  - Tool contract: `tool.validate` (direct) or `tool.fallback`
  - Prompt regression: `prompt.edit` (direct) or `revert`
- The active fault requires tenant match **and** window overlap **and** a cohort
  key match. For the prompt fault the cohort key must be `agent_id`; passing only
  an intent yields no fault and therefore `no_effect`.
- A wrong fix and an inactive cohort return the **same** `no_effect`. This is
  deliberate: 40 free probes must not map the faults.
- `before` is seeded noise, not your corpus number. Do not treat it as
  confirmation of your measurement.
- A correct fix can randomly report `golden_set.pass = false` (small per-session
  break probability). The `verdict` stays `improved`; do not spend attempts
  retrying on `pass=false` alone.

### What to do with it
1. Do all diagnosis offline first.
2. Pick the highest-confidence fix (the silent-tool `tool.validate` is the
   strongest in the kit).
3. Freeze a golden set of known-good sessions before proposing.
4. Send **one** request on the exact detected cohort and window.
5. Persist `run_id`, `before`, `after`, `golden_set`, `verdict`, and
   `prediction_error` into `verifications`.
6. Spend a second attempt only on a genuinely different valid fix, or to recover
   from an input mistake.
7. Record `no_effect` honestly. A wrong fix returning no effect is a valid result.

## 9. The sealed run

- **Day 6, 12:00: everything freezes.** The system runs untouched on a second
  dataset with the same kinds of problems planted on different days, tenants, and
  slices of traffic. The answer key is held by the organisers.
- **That output is what gets scored.** A system needing hand-holding scores as if
  it failed.
- The official requirement says tenants and slices move, so **never hardcode
  practice tenant/day/intent/tool/agent values**; derive cohorts from the data and
  the config timeline.
- Caveat found in the kit: the *shipped* `sealed_schedule()` generator
  (`nlkit/world.py`) keeps tenants/cohorts/cause classes fixed and only moves
  days/lengths/rates. Design for the stricter official behaviour anyway, because
  the organisers control the real sealed corpus and its passphrase.

## 10. Scoring and levels

| Points | Criterion | Scored by | What it asks |
|---:|---|---|---|
| 20 | Diagnostic accuracy | script | Right problem, slice, cause, and how late noticed |
| 15 | Specificity | script | No false alarms on lookalikes; credit for explicit dismissal |
| 12 | Honesty | script | Fidelity+coverage on every metric, calibration ≠ 1.00, correct refusal with usable event spec |
| 8 | Loop completeness | script | Detect→diagnose→prescribe→verify linked and unattended |
| 18 | Decision quality | people | Can an operator act; every impact figure traceable; baseline named |
| 15 | The screen | people | Can a stranger read, see evidence, approve/reject |
| 12 | Framing | people | Demo opens on the problem, shows the refusal, states coverage, admits what is faked |
| **100** | | | |

Levels (reference reports in the kit, scored by `score.py`):

| Level | State | Machine |
|---|---|---:|
| Start | `starter.py`: 2 metrics, honest coverage, valid file | 9.8 |
| Level 1 | One real problem quantified+explained, three lookalikes dismissed, A11 refused | 38.0 |
| Level 2 | + mined standard, one fix proposed and replayed | 41.5 |
| Level 3 | + other problems found, human decision recorded, self hit-rate | 46.3 |

PS guidance: "A Level 1 with an excellent screen and decision layer scores about
70 of 100. A Level 3 with neither scores about 58." So the 45 human points matter
as much as the machine half; do not over-invest in detection at the expense of
the screen, decision, and framing.

## 12. Related questions, answered

**Do we need a backend/platform?**
No. A pipeline plus a single local screen/API is enough. You need a server only
so the approve/reject action can modify the report; a static page cannot.

**Must we run an LLM?**
No. In fact Rule 1 forbids using one for facts already in the logs. An LLM judge
is optional and only for meaning (e.g. A09 frustration reason). The cheapest
honest path for A09 is a `REQUIRES_NEW_JUDGE` gap. If you do build a judge,
version it and publish agreement with the kit's human labels, and never report 1.00.

**What is judged by script vs people?**
Script: accuracy 20, specificity 15, honesty 12, loop 8 = 55. People: decision
quality 18, screen 15, framing 12 = 45.

**Can we change a metric definition to make a fix look better?**
No. Rule 2: the yardstick (metric definitions, judge versions, reviewed good set)
is fixed. Changing it is disqualifying. You may propose changes to the agent only.

**What happens if we don't use all 40 replay attempts?**
Nothing bad. Budget is a cap, not a target. Use as few as possible; one
well-formed, diagnosed replay beats forty probes.

**Is `before` from replay comparable to our measured value?**
No. It is seeded noise for the simulation. Report it as replay evidence, not as
corroboration of your corpus measurement. `prediction_error` may be large; record
it honestly.

**What if our fix returns `no_effect`?**
Record it as the verification verdict. It is a valid result. The scorer awards
loop points for a real replay even when the verdict is `no_effect`, and human
judges reward honest reporting.

**Do we have to detect all three faults to do well?**
Accuracy is 20/3 per fault and the reference ceiling is 46.3 with only two faults
found. All three plus all three lookalikes is how you approach full machine
points. But the PS says "depth on one problem beats breadth" and the human half is
45 points — so the winning shape is all three detected and dismissed, with depth
(standard + fix + replay + decision) on one.

**What is the one thing that disqualifies us fastest?**
Using an LLM for logged facts (Rule 1), or moving the yardstick (Rule 2). Also, a
sealed run that needs a human to run it.

## 13. Do we build an agentic framework? Do we need an LLM at all?

Short answer: **no agentic framework, and almost certainly no LLM.** The
"agentic" part of this problem is the *reasoning about an agent's tools, KB,
prompts, and handoffs* — not building another agent. The PS explicitly warns
against the reflex: "The goal is not simply to find unusual numbers" and Rule 1
forbids asking a model what the logs already record. A deterministic Python
pipeline is the intended architecture. If
you build a swarm of LLM agents here you will (a) violate Rule 1 on the easy
facts, (b) make the sealed run non-reproducible and slow, and (c) score nothing
extra, because no rubric line rewards orchestration.

### 13.1 The rule that governs everything

Rule 1 (PS p.6, "TWO RULES YOU CANNOT BREAK"):

> Never ask a language model something the logs already record. Whether an API
> returned an error, which model served a turn, whether a handoff happened:
> these are facts in the data. Use a model only for questions of meaning: was the
> user satisfied, was the answer correct, what was this conversation about.
> Version any judge you build, and publish how often it agrees with the human
> labels in the kit. Breaking this rule is disqualifying.

So the decision is not "should we use an LLM for the pipeline" — it is "is any
required output a question of *meaning* rather than a logged fact." Most are not.

### 13.2 Work that must stay deterministic (no LLM, ever)

All of detection, quantification, and attribution is logged fact:

- containment, resolution, handoff, abandonment, turns, duration, cost;
- tool failure rate, empty-success / `result_field_count == 0`, retries, latency;
- KB hit rate and KB top score;
- session-end and `handoff_by_design`;
- cohort/window definition, before/after baselines, peer selection;
- config-change matching and the `attributed_change`;
- impact counts, share of traffic, downstream counts, cost rollups;
- the standard's numeric `best`/`median`/`deficit`;
- the replay call and its returned `before`/`after`/`verdict`;
- the A11 refusal (it is a capability determination from the catalog, not a
  semantic question).

If any of these numbers appears in the report, it must come from a query over
the corpus, never from a model. This is also the *cheapest* path: they are all
simple aggregations.

### 13.3 The only places an LLM judge could legitimately help

These are optional. None is required for a 55/55 machine score or a strong human
score. Do them only if you want the extra ask coverage and can calibrate them.

| Where | Ask | What the judge does | Required output |
|---|---|---|---|
| Abandonment reason | A09 | Classify *why* an abandoned session ended (frustration vs. got what they wanted vs. other) from the last few turns | Judged metric with `fidelity: judged`, a `judge_version`, and `calibration{agreement,n}` |
| KB "actually answering" | A06 | Judge whether a KB-grounded answer actually addressed the question (the measured `kb_hit`/`kb_top_score` is a different reading) | Judged secondary reading, or just offer the measured one |
| Review queue | A10 | Rank already-scoped conversations by a semantic quality/frustration score | A deterministic scope composed with a judged score |
| Response correctness / satisfaction | (none required) | General quality audit | Only if it feeds a required ask |

Note the cheapest honest move for **A09** is *not* to build a judge: emit a
`gaps` entry with `verdict: REQUIRES_NEW_JUDGE` and explain that abandonment is
measured but the reason is a meaning judgment needing its own versioned rubric.
The scorer accepts that as the correct fidelity (`score.py:305-308`), and it
demonstrates exactly the intellectual honesty the rubric rewards. Build the judge
only if you want to show the judged metric as well.

### 13.4 If you do build a judge, build it like this

1. **One judge per semantic task.** Do not use one generic agreement score for
   outcome and quality and frustration. They are different tasks.
2. **Input is text only** (turns), plus no logged fact the model could otherwise
   read — you are asking about meaning, not state.
3. **Fixed prompt + rubric + model + temperature**, stored as a version string
   (e.g. `frustration_judge_v1`). The version is what makes it reproducible and
   what lets you refuse cross-version comparisons.
4. **Calibrate against the kit's human labels.** `labels/outcome_labels.jsonl`
   (400 rows) and `labels/rubric_scores.jsonl` (~100 rows, plain JSONL, not
   gzipped). Compute agreement on a held-out split, publish `agreement` and `n`
   in the metric's `calibration` block.
5. **Never report 1.00.** Human labellers disagree ~7.5% of the time
   (`labels.py`), so a perfect score is a bug. Verified anchors from the kit:
   outcome-label agreement ≈ 0.91; human-vs-machine rubric MAE ≈ 0.44
   (within-1 ≈ 0.95), v1 MAE ≈ 0.50, v2 MAE ≈ 0.37.
6. **The judge may only produce a label/score, never a number that goes into an
   impact or diagnosis field.** It cannot invent conversation counts, costs, or
   baselines. Deterministic code owns every figure.
7. **Cache and run offline.** The sealed run must not depend on a live API.
   Commit the judge outputs (or the stub) so the pipeline is reproducible. If you
   use a hosted model, treat the report as a build artefact with recorded model
   version and seeds.
8. **Label it in `system_notes` and the one-page note.** If the judge is stubbed
   from the supplied labels, say so. "Faking is fine; hiding it is not."

### 13.5 The "agentic" framing that actually helps your score

Do not build a tool-calling agent that scans the corpus. Instead, show *agentic
understanding* in the findings themselves:

- "the tool call succeeded but the agent received no usable information"
  (transport success vs. application contract);
- "the agent's own retry of the same tool is corroborating evidence" (retry is
  not failover);
- "a prompt change raised cost and turns while outcomes stayed flat";
- "a new intent was born broken with no KB coverage, so its baseline must be peer
  traffic";
- "this is a mix shift / load event / judge-version change, not a regression."

That is what the 45 human points reward. An orchestration diagram of LLM agents
rewards nothing.

### 13.6 Recommendation

- **Agentic framework:** none. Deterministic Python modules (see
  `docs/solution-overview.md`). No LangChain/CrewAI/AutoGen, no tool
  loop, no vector DB.
- **LLM work:** zero required. Use supplied labels for the one calibration the
  honesty section wants (quality), and answer A09 with a `REQUIRES_NEW_JUDGE`
  gap. Optionally add at most **one** calibrated judge if you specifically want
  to demonstrate the A09 judged reading.
- **Where the effort should go instead:** all three faults, all three
  lookalikes, the standard, one replayed fix, and the decision screen.
