  • get_order_status: 13.7% of outcome='ok' calls returned status 200 with result_field_count = 0 on days 40-51, against 0.0% outside the window (z=21.0, 2779 calls in window)
  • declared tool_error_rate on get_order_status is flat across the break: 0.016 in window vs 0.021 outside — the fault is invisible to the error metric
  • same-tool retry (retry_count > 0 on a second get_order_status call in the session) in 0.130 of affected sessions vs 0.000 before the window
  • cohort resolution_rate 0.7755 in window vs 0.8547 baseline (this cohort's own resolution over the 14 days before the break)
  • config_timeline day 40: kind=tool target=get_order_status 3.2.0 -> 3.3.0 'order service migration'

6Diagnosis

tool.contract_break · confidence 0.90 · attributed: tool on day 40 (3.2.0 → 3.3.0)

  • status_code 200, outcome 'ok', result_field_count 0: transport success, application failure — the agent received nothing to answer with
  • ordinary error_class taxonomy never fires, so alerting on tool_error_rate misses it
  • the runtime's own same-tool retry inside the session corroborates the empty answer
  • onset aligns with the get_order_status 3.2.0 -> 3.3.0 deploy on day 40

7Proposed change

tool.validate on get_order_status · predicted resolution_rate 0.7755 → 0.8468

Validate the get_order_status response before handing it to the model: a 200 with result_field_count = 0 is treated as upstream.malformed_response, the existing fallback path is taken, and the empty answer is counted as a tool failure. 13.7% of 'ok' calls were empty in the window.

Asking approval for. Make get_order_status reject an empty HTTP 200 as a failure and take the existing fallback path, instead of letting the agent apologise with nothing to say.

Risk if the diagnosis is wrong. Moderate. If some records legitimately return an empty payload (a brand-new order, a cancelled one), we would start treating a valid state as an error and route those users to a human unnecessarily. Confirm with the owning team that an empty 200 is never a valid state.

Would not ship if. The upstream team confirms empty 200s are a valid state, or the empty-payload rate has already fallen after their own fix — then we would be patching a contract about to change again. Alternative: tool.fallback (route empties to a fallback copy path without changing failure accounting).

Design read — what felt right, and why

This is the "ideology" bit. It is a decision surface, not an analytics dashboard.

  1. One decision at a time (1). The screen opens on a single, already-diagnosed finding. A list of eleven charts makes an operator triage; a single call makes them decide.
  2. Primary finding first, everything else secondary (2, 9). The regressions that matter are promoted; load spikes, mix shifts, judge changes and refusals sit in a quiet column so the eye lands on what needs a signature.
  3. Every number is copied, never computed (3). The report is the source of truth. If the screen and the report ever disagree, the screen is wrong.
  4. Impact in the operator's units (4). Conversations, share of tenant, days running, and a real cost — not just the model metric. "resolution_rate 0.7755" means nothing to a duty manager; "2,686 conversations, 12 days, $94.31" does.
  5. Pre-empt "compared to what?" (5). The fairness of the baseline is shown inline, in plain words, because that is the first objection any real reviewer raises.
  6. Diagnosis before prescription (6). The cause class, its confidence, and the attributed change appear before the proposed fix, so the fix is never read without its reasoning.
  7. The proposal forces three questions (7). What am I approving, what breaks if the diagnosis is wrong, and when would we not ship. If those can't be answered, there is no proposal worth a gate.
  8. The gate is the product (8). Accept / reject / defer needs a written reason and writes back into prescriptions[].approval — an auditable record, not a button that logs a click. Approve is the only confident action.
  9. Refusal is a first-class result (9). A09/A11/A02 render as "refused — here is the required event, here is the tempting proxy, and here is why it lies." Showing a number we cannot stand behind is worse than showing none.
  10. Verification is attachable, not mandatory. Replay is shown as an attached artifact and may be absent; its removal must not change the finding. The decision record stands on its own.
